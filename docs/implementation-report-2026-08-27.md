# 截图工坊本轮改造报告

日期：2026-08-27

## 一、结论

本轮已完成主要方案改造，但尚未达到“任意说唱音频都能自动严格逐句同步”的最终目标。

当前系统已经具备：

- 新电脑依赖探测与补齐能力
- 音频统一标准化
- ASR 多级回退
- 说唱拖音、复唱、副歌和 ad-lib 的 Agent 复核上下文
- ASR 失败/低置信度质量闸门
- 断点续跑和已有产物复用
- 多种脚本说话人格式兼容
- 真实视频生成回归能力

仍未完全解决：

- faster-whisper/CTranslate2 在部分 Windows 环境下加载模型时的访问冲突
- 基于已知歌词文本的真正强制对齐
- 复杂歌曲中的多人声、重复副歌和伴奏覆盖的全自动判断
- 前端构建所需依赖构建脚本被 pnpm 安全策略阻止的问题

## 二、本轮已完成改造

### 1. 音频标准化

新增统一音频处理模块，将输入音频转换为：

- 16 kHz
- 单声道
- PCM signed 16-bit WAV

BeatGrid 和 Whisper 使用同一份标准化音频，避免 MP3 VBR 时长、采样率和声道差异造成时间轴偏移。

相关文件：

- `mcp-server/tools/audio.js`
- `mcp-server/tools/beatGrid.js`
- `mcp-server/tools/transcribe.js`
- `test/audio.test.mjs`

### 2. ASR 多级策略

ASR 现在会尝试多种运行配置：

1. 配置模型和计算类型
2. `base`
3. `tiny`
4. `float32` 计算类型回退

失败时会保留模型、计算类型、退出码和 Python stderr，避免只显示笼统的 `Command failed`。

注意：ASR 运行失败与 ASR 文本匹配质量不足现在已经分开记录。

### 3. 说唱特征处理

Agent 复核上下文现在包含：

- ASR 段级时间
- ASR 词级时间
- 完整 mapping
- 相邻重复段候选
- ASR 运行状态和错误

复核提示明确要求 Agent 区分：

- 拖音
- 复唱
- 副歌重复
- ad-lib
- 真正的识别错误

重复内容不再默认合并，拖音的结束时间也不再按文字长度强行截断。

### 4. 质量闸门

默认情况下，只要出现以下任一情况，就不会直接交付正式视频：

- ASR 执行失败
- ASR 置信度不足
- mapping 存在未匹配项
- mapping 存在歧义
- mapping 存在低置信匹配

如确实需要观察近似效果，必须显式使用：

```powershell
node scripts/agent-bridge.mjs run --allow-approximate ...
```

近似视频会写入：

```text
delivery_mode=approximate_preview
```

并带有明确警告。

### 5. 断点续跑

Planner 现在会根据以下条件判断是否复用已有产物：

- 项目 ID 相同
- 脚本文本相同
- 音频路径相同
- 已存在脚本消息
- 已存在 align mapping

满足条件时：

- 不重复解析脚本
- 不重复运行 ASR
- 不覆盖 Agent 已修正的 mapping
- 直接进入后续复核或渲染

### 6. 脚本格式兼容

解析器现在兼容：

```text
A说：你好
[A] 你好
A: 你好
```

内部会统一转换为聊天消息对象。

### 7. 启动和新电脑体验

已处理：

- Windows 下 Vite 不再通过 `npm.cmd/cmd.exe` 启动，减少控制台闪烁
- 自动探测用户目录中的 Python 3.10+
- 自动探测常见 FFmpeg 路径
- FFmpeg 输出目录不存在时自动创建
- FFmpeg 提前退出时输出更明确的错误
- ASR 模型支持 `setup-asr` 预载

## 三、当前真实同步链路

当前实际链路是：

```text
输入音频
  -> FFmpeg 标准化 WAV
  -> faster-whisper ASR
  -> 词级时间戳
  -> 脚本文本与 ASR 词群有序 DP 匹配
  -> Agent 复核重复/拖音/ad-lib/歧义
  -> 时间轴校验
  -> Canvas + FFmpeg 渲染
```

其中：

- 脚本是权威台词
- ASR 提供实际发声时间
- BeatGrid 是节奏参考，不应覆盖真实发声边界
- Agent 负责语义判断和异常处理
- 渲染器只消费最终时间轴

## 四、已知限制

### 1. Windows ASR 运行时问题

本机曾出现：

```text
exit code -1073741819
```

对应 Windows 访问冲突，发生在 CTranslate2 加载 Whisper 模型阶段，不是 DP 算法错误。

系统现在会尝试备用模型和计算类型，并记录真实错误；如果全部失败，会进入质量闸门，不再伪装成严格同步结果。

### 2. 强制对齐尚未完成

当前仍属于：

```text
ASR 时间戳 + 文本相似度 + 有序 DP + Agent 复核
```

更高阶的方案应是：

```text
脚本作为固定目标文本
ASR 只作为时间候选
结合词间停顿、语速、能量和顺序做强制对齐
```

这将是后续提高说唱同步质量的主要方向。

### 3. 说唱音频本身的识别边界

以下情况无法仅靠普通 ASR 保证严格同步：

- 歌词与脚本不一致
- 多人同时演唱
- 强伴奏覆盖人声
- 大量拖音和无意义音节
- 副歌重复但脚本只写了一遍
- ASR 模型无法稳定加载

这些情况必须依赖 Agent 或用户审阅时间轴。

## 六、未完成项与建议顺序

1. 修复或隔离 Windows CTranslate2 访问冲突
2. 增加真实 ASR 质量指标，而不仅是“是否有词”
3. 实现基于脚本的强制对齐
4. 为副歌重复和 ad-lib 建立显式事件模型
5. 让 Agent 审核完整时间轴并输出最终确认状态
6. 完善从任意失败步骤恢复的产物校验
7. 解决 pnpm ignored build scripts 导致的前端构建问题

## 七、最终判断

本轮不是简单调参，而是把系统从：

```text
ASR 失败也继续生成
```

改成：

```text
ASR/对齐失败 -> 明确暴露 -> Agent/用户复核 -> 确认后渲染
```

这解决了“程序显示成功但视频实际不同步”的产品风险，也为后续真正的说唱强制对齐保留了正确的架构边界。
